## P1: 우선 수정이 필요한 결함

### 1. 포지션 조회 실패를 포지션 없음으로 반환

- 위치: `src/aurora_ict/bot/aurora_adapter.py:393`, `:424`; `bot_trend_instance.py:730`; `bot_ict_instance.py:4379`.
- 1차 조회와 대체 조회가 모두 네트워크/호출 제한 오류를 내면 어댑터는 `None`을 반환한다. 인증 오류만 별도로 전파한다.

- 영향: 거래소에는 포지션이 남았는데 장부와 봇만 종료될 수 있다. 조회 실패와 실제 수량 0을 구분하는 계약이 필요하다.

### 9. 사용자가 낮춘 일일 손실 한도가 재생성 때 유실

- 위치: `src/aurora_ict/api/app.py:1290`; `src/aurora_ict/bot/multi_user_manager.py:219`.
- API는 현재 슬롯/봇만 바꾸고 사용자 DB에는 저장하지 않는다.
- 실제 API와 실제 설정 재구성 함수에서 **사용자 요청 2% -> 실행 객체 2% -> 같은 사용자 재구성 15%**를 재현했다.
- STOP/START, 키 교체 후 재가동, 배포 등에서 더 낮은 사용자 한도가 사라질 수 있다. 슬롯이 없을 때는 적용 대상 없이 성공 응답도 가능하다.
- Cursus는 일일 누적 상태도 메모리에만 있고, 무포지션 진입 검사와 달리 `_reverse -> _open` 경로에는 한도 검사가 없다. 한도가 0이면 비활성인 조건을 구분해야 한다. 구독 설정은 기본 15% 한도를 적용한다.

- INSERT 뒤 commit 실패 시 rollback 없이 INSERT부터 다시 시도한다.
- 실제 SQLite 읽기 트랜잭션 잠금과 실제 기록 함수로 재현했다. 잠금 해제 뒤 다음 기록에서 **JSONL 2건, SQLite 4건**, 첫 손절 -10이 세 번 기록되어 해당 SQLite 손익 합계가 -30이 됐다.
- JSONL이 원본 장부이므로 원본까지 같은 중복이라고 단정하지 않는다. 이번 운영 관측에서 해당 잠금 사고나 기존 중복 장부를 확인한 것은 아니다.

### 13. 주문 자료형 변환에서 주문 ID/체결 정보 유실

- 위치: `src/aurora/exchange/base.py:51`; `src/aurora/exchange/ccxt_client.py:825`; `src/aurora_ict/bot/aurora_adapter.py:328`.
- 실제 `Order`는 slots dataclass인데 어댑터는 `__dict__`/dict만 처리해 나머지를 문자열 `raw`로 만든다.
- 실제 주문 파서/어댑터에 합성 주문을 통과시키자 결과 키는 raw뿐이고 주문 ID가 사라졌다. 체결 정보는 파서 단계에서도 보존되지 않는 항목이 있다.
- 보완 포지션 조회가 체결가/수량을 찾을 수 있으므로 항상 체결 정보를 잃는다는 뜻은 아니다. 하지만 대기 주문/미체결 시 주문 추적 계약이 약해진다.

### 14. 관리자 대기 주문 화면에서 Cursus 누락

- 위치: `src/aurora_ict/api/app.py:1578`; `src/aurora_ict/bot/bot_trend_instance.py:185`.
- 관리 API는 `_pending_entry`만 읽지만 Cursus 실제 대기는 `_pending_limit`에 저장한다. 호환용 `_pending_entry`는 None이다.
- 관리 API의 대기 0건만으로 실제 Cursus 대기 주문이 없다고 판단할 수 없다. 이번 감사에서는 별도 거래소 읽기로 확인했다.

### 15. Origo 진입 전 봉 고가가 본전 손절 이동을 촉발

- 위치: `src/aurora_ict/bot/bot_ict_instance.py:2742`.
- 실제 본전 이동 함수에 10:00 봉 고가 103, 10:04 진입가 100, 초기 SL 98, 현재가 100.2를 넣으면 SL 100으로 이동하고 본전 이동 완료가 된다.
- 봉 고가가 진입 전에 발생했을 가능성을 제외하지 않아 진입 후 1R 도달 근거가 부족하다. 실거래 발생 횟수는 측정하지 않았다.

## 검증과 감시

- 새 재현은 실제 함수와 결정론적 합성 입력을 사용했다. 공통/Cursus 재현에는 실제 어댑터, 실제 수량 정밀도 또는 실제 SQLite를 연결했다. 실거래 API/모의 객체 프레임워크를 사용하지 않았다.
- 기존 테스트는 수정하지 않고 관련 8개 파일을 실행했다. **198 passed, 11 warnings, 29.43초**였다. 경고는 기존 AsyncMock의 동기 수량 정밀도 함수 처리에서 발생했다. 통과 여부만으로 실제 어댑터 반환 계약이나 수량 간격 검증을 대신할 수 없다.
- **19:43~19:58 KST, 15분 감시 완료**: health 55/55회 HTTP 200, 수집 로그 1,371건, heartbeat 94건. 실행 이미지/머신 버전 464는 전후 동일했고 종료 시 1/1 상태 검사 통과였다.
- 수집 로그에서 잔고 부족 110007, 권한 거부 10005, 정밀도 오류, traceback, 메모리 오류는 각각 0건이었다. 신규 진입/가용액 조회 로그도 관측되지 않아 잔고 수정 후 신규 실주문 검증을 완료한 것은 아니다.
- 33004 키 만료 관련 로그는 132건이었다. 이는 계정 수나 독립 사고 수가 아니다. 자동 재가동 뒤 만료 키로 다시 인증 실패/정지하는 기존 미해결 경로도 관측됐다.
- 진단 자료: `data/system_audit/shared_contracts.json`, `admin_snapshot.json`, `exchange_snapshot.json`, `monitor.json`; Cursus 상세 재현은 `data/cursus_audit/`, Origo는 `data/origo_audit/`, 설정/장부는 `data/lifecycle_audit/`.
- 감시는 HTTPS health와 Fly 로그 읽기 전용 수집이다. 매회 최근 로그를 가져오므로 빠른 로그 폭증 시 누락 가능성이 있다. 관측된 오류 0을 전체 기간의 오류 부재 증명으로 쓰지 않는다.
- 이번 15분 감시는 상시 감시 서비스 설치가 아니다. 종료 시점 이후 자동 감시/자동 수정은 약속하지 않는다.
- Bybit 주문 접수는 비동기이며 시장가 주문도 IOC로 처리될 수 있다. 주문 응답만으로 전량 체결을 가정할 수 없다. [Bybit 주문 생성](https://bybit-exchange.github.io/docs/v5/order/create-order)
- 거래소 손절 보호는 등록된 조건부 주문 기준이다. [Bybit Trading Stop](https://bybit-exchange.github.io/docs/v5/position/trading-stop)

## 수정 우선순위

1. 공통 조회/취소의 미확인 상태를 보존하고 실제 잔량 확인 전 추적/장부를 종료하지 않는다.
2. Cursus TP/비상청산과 Origo 부분체결/지정가 보호를 묶어 실패, 지연 체결, 수량 간격까지 검증한다.
3. 모델 유예, 사용자 한도, TP 진행의 영속 복원을 구현한다.
4. 마감봉 정합, 시간봉 격리, 장부 재시도, 관리자 관측을 고친다.

코드 수정과 운영 개입은 이번 점검에 포함하지 않았다. 인증 실패 계정과 미추적 무손절 포지션은 사용자 확인이 필요한 운영 항목이며 임의로 변경하지 않는다.
